# План внедрения пользователям

## Этап 1. Зафиксировать кандидат

1. Использовать очищенный снимок LIVE из этого выпуска; действующий LIVE не заменять сборкой.
2. Зафиксировать код новой историей Git, версию приложения, версию userscript и SHA256.
3. Выполнить установку зависимостей в отдельной чистой Python 3.12 x64 среде, `pip check`,
   тесты обновления и проверки синтаксиса. Собрать Windows onedir на Windows.
4. Подготовить Windows ZIP, source ZIP, суммы, changelog и инструкции подключения компонентов.
5. Проверить отсутствие ключей, проектов, `.env`, баз, логов и старой Git-истории в архивах.
6. Создать приватный репозиторий и черновик pre-release. Не выдавать его как стабильный релиз.

## Этап 2. Пилот на отдельном компьютере

1. Выбрать одного тестировщика; дать доступ к private Releases или передать архив отдельно.
2. На Windows x64 без Python проверить запуск portable с пустыми данными.
3. Ввести свои ключи и настроить инструмент Flow по инструкции. Проверить мост и генерацию
   одного персонажа/кадра, затем одну анимацию. Результат неизвестного запроса не повторять.
4. Установить отдельный набор Qwen/CUDA для своего GPU. Проверить анализ изображения и видео,
   отказ при нехватке VRAM без падения монтажа. Запас VRAM одного ПК не гарантирован на всех ПК.
5. Прогнать мини-проект из 3–5 сцен: озвучка → генерация → фото/футаж → подбор → вставка целым
   сегментом → скрыть/удалить футаж → вернуть сгенерированный кадр → Undo → экспорт MP4.
6. Обновить копию предыдущей установки: проекты/кадры/настройки/DPAPI-ключ сохранились,
   резервная копия проверена. Проверить восстановление в отдельный data.
7. Отдельно проверить путь с пробелами/кириллицей, занятый порт, повторный запуск,
   отсутствие сети, неверный API-ключ и недоступность Qwen.

## Этап 3. Критерии допуска

- Нет потери исходных кадров, озвучки, монтажных правок и файлов проекта.
- Длина таймлайна при включении/выключении футажа сохраняется.
- Не отправляются дубли неизвестных Flow-запросов.
- Новый экземпляр и обновление не запускаются одновременно с прежним на том же data.
- Пользователь может восстановить старую версию из полной копии.
- Дистрибутив содержит нужные уведомления/лицензии сторонних компонентов.
- Проверено подключение Flow отдельным пользователем и реальный MP4 на его ПК.

Результаты помечать по каждому пункту «пройдено / не проверено / ошибка», с номером сборки.
Локальные измерения одного ПК не заменяют пилот.

## Этап 4. Рассылка и поддержка

1. Опубликовать pre-release для 2–3 пользователей, затем расширять после проверки.
2. Отправлять ссылку Releases, короткую инструкцию обновления и список совместимых компонентов.
3. Сохранять предыдущий рабочий выпуск. Не заменять ZIP существующего тега новыми байтами:
   при исправлениях выпускать новый номер и новые суммы.
4. В отчётах просить версию, этап, ОС/GPU и обезличенную ошибку. Не просить API-ключи/базы.
5. После успешного пилота выпускать стабильную версию отдельным тегом, например `v0.2.0`.

## Следующий этап: автоматическое обновление

В кандидат входит **ручное скачивание + безопасная подготовка обновления**, не фоновый updater.
Для private GitHub понадобятся отдельная авторизация пользователя/загрузчик,
подписанный манифест, проверка архива до распаковки, атомарное переключение версии,
контроль миграций и тесты прерывания на каждом этапе. Токен владельца в EXE не встраивать.

Зависимости/модели обновлять отдельными изменениями: новый lock → чистая установка →
регрессии монтажа/Flow/анализа → сборка → пилот. `pip install --upgrade` в LIVE не выполнять.
